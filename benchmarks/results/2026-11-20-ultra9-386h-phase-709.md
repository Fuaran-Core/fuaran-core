# One preorder for a registry's per-node families — 2026-11-20 — Core Ultra 9 386H — Phase 709

Phase 709 made `RuleFamily` opaque behind two constructors, `Validator.wholeTree` and `Validator.perNode`, so that
`Validator.runAll` can tell a per-node family from any other and run every per-node family of a registry over one
preorder of the tree. [Phase 615](2026-11-19-ultra9-386h-phase-615.md) measured what that could buy, and found
that the change could not be additive. This file is the before and after.

**Result.** At 5,021 nodes and 30 per-node families, `runAll` allocates 4.8 to 5.0 MB a call, down from
18.9 MB, and takes about 2.3 ms, down from 6.9 to 11.8 ms in the same session. The allocation figure does not
depend on the machine's load. The time figure does: see the note on load below.

## Method

- **Harness:** Phase 615's, [`walks-phase-615.fsx`](walks-phase-615.fsx), unchanged, run as its header says, one
  case at one size per process. Before timing anything its `runAll` case checks that `runAll` returns a non-empty
  defect list equal to the one-walk bound's, so a run that did no work cannot be reported. That check passed on
  both trees.
- **Before and after, interleaved.** The same checkout was built in Release twice per round: once with
  `Validator.fs` as it stood at `abd6034c` (the branch base, before this phase), once with this phase's
  `Validator.fs`. Each build was followed by its cases. Two rounds were taken, so each figure below appears twice,
  and a reader can see how far the time column moves between two runs of the same binary.
- **Machine:** Intel Core Ultra 9 386H, 16 logical processors, Windows 10.0.26300. The machine was running other
  builds and test runs throughout, and no benchmark lock was taken. Read the time columns as a range, not a point;
  the allocation column is what this file stands on.
- **.NET:** runtime 10.0.8, SDK 10.0.203.
- **Columns:** Phase 607's: wall time per call in milliseconds (mean, median, p95), the bytes the calling thread
  allocated per call, and generation-2 collections per call.

## What the figures say

- **The 29 extra preorders are gone.** At 5,021 nodes the shipped call allocated 18.9 MB; it now allocates 4.8 to
  5.0 MB. Phase 615 put the 29 extra preorders at about 13.9 MB (29 × 480 KB), and the drop here is 13.9 to 14.1 MB.
- **The call now beats the harness's own bound.** Phase 615's "one preorder" case, the bound a shared walk could
  reach, allocates 8.7 MB, because it builds its list through a sequence expression and copies each defect to stamp
  it. `runAll` stamps through the walker it always used, so it lands below the bound the harness states.
- **Time follows allocation, as far as this machine can show it.** The two after rounds agree (2.33 ms mean at
  5,021 nodes); the two before rounds do not (6.9 ms and 11.8 ms), which is the machine's load, not the code. Every
  after figure is below every before figure at both sizes.
- **No gen2 collection** occurred in any case at either size.

## What would reopen this

A consumer whose families are whole-tree in form but per-node in substance (a `Run` that maps a rule over a
preorder of its own) pays every walk it makes, as before: the walker cannot share what it cannot see. Restating
such a family with `perNode` is the consumer's change, and this harness, with the consumer's families in place of
the 30 synthetic ones, is how to measure what it buys.
