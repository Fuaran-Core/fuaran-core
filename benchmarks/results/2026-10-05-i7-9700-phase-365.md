# Wire layer timing — 2026-10-05 — i7-9700 — Phase 365 (the escape's fast path)

Phase 365 changed how a string is escaped. `Json.escape` now scans for the first character it has to
escape, returns a string with none as it is, and otherwise appends each clean run whole. The writer
escapes into its own builder (`Json.escapeInto`). The same scan is in the two D2 copies of the rule
(`JsonString.quote`, the DAG's `jstr`). No emitted byte moves. The "before" is the tree this phase
started from; the Phase 364 baseline is [`2026-10-04-i7-9700-phase-364.md`](2026-10-04-i7-9700-phase-364.md).
How to run and read the tables: [`docs/wire-performance.md`](../../docs/wire-performance.md).

- **Machine:** Intel Core i7-9700 @ 3.00 GHz, 8 logical processors, Windows 10.0.26200, mains power.
- **.NET:** SDK 10.0.401, Release build of `benchmarks/Fuaran.Core.Wire.Benchmarks`.
- **node:** v25.9.0. **Fable:** 5.0.0 (fable-library-js 5.0.0), from the toolchain of a checkout that
  owns one, compiling the harness to a scratch directory (DECISIONS.md D55). Each tree was compiled
  separately.
- **Trees:** before, fuaran-core `phase-365` at `b97fc3b` (no change to `src/`); after, the same branch
  with this phase's `src/` changes.
- **Command:** `pwsh ./benchmarks/run.ps1 -Runs 15 -NodeEntry <fable output>/Program.js`, run twice back
  to back for each tree on an otherwise idle machine.
- **Agreement:** in all four runs, the 16 case fingerprints were identical on .NET and node and matched
  the pins in `Corpus.fs` before anything was timed. The escape's output did not change.

Figures are the median of 15 samples, in milliseconds per call.

## Under Fable: the regex scan against the loop

The phase allowed the scan to be one native regex search under Fable if the harness showed it faster
than the loop. Both were compiled and timed, two runs each (node, ms per call):

| corpus | escape, loop | escape, regex | render, loop | render, regex |
|---|---:|---:|---:|---:|
| escape-free | 0.211 / 0.219 | 0.123 / 0.117 | 0.398 / 0.445 | 0.391 / 0.375 |
| escape-heavy | 1.781 / 1.844 | 1.875 / 1.812 | 2.094 / 2.375 | 2.219 / 2.094 |
| op-stream | 0.531 / 0.531 | 0.547 / 0.531 | 3.625 / 3.687 | 3.688 / 3.625 |
| state | 0.758 / 0.711 | 0.711 / 0.703 | 5.312 / 5.313 | 5.313 / 5.750 |

The regex roughly halves the escape of long clean strings (`escape-free`) and is level, within the
spread, everywhere else: short strings and strings with an early escape leave the scan little to do.
It is the one that shipped. Its output was checked under node against a one-character-at-a-time
oracle over 462,144 strings (every UTF-16 code unit alone and inside runs, and 200,000 random strings
of quotes, backslashes, controls, surrogate pairs and lone surrogates), with no mismatch; a variant
that drops one character was red on every string.

## What the figures say

- **Escape-free strings no longer cost a copy.** The .NET `escape-free` and `state` escapes allocate
  24 bytes per call, the boxed total, because every string is returned as it is. The escape case is
  2.4 to 5.5 times faster on .NET and 4.7 to 21 times faster under node (each range the faster
  "before" over the slower "after").
- **Render allocates about half what it did.** Each string is escaped straight into the writer's
  builder, so no intermediate string is made per value. The 20,000-token state renders with 3.5 MB in
  place of 6.6 MB. Render is 1.25 to 2.7 times faster on .NET and 2.8 to 7.3 times faster under node.
- **Escape-heavy text is still the dearest per character**, because each escaped character is one
  append. Under node it now costs about 15 times escape-free text, against about 3.5 before; the
  escape-free cost fell much further than the heavy one.
- **The node ÷ .NET escape ratio fell** from 3.3–13.3 before to 2.2–5.1 after, and render's from
  3.6–9.4 to 2.0–5.6.
- **Parse did not move,** as expected: its code is unchanged. The .NET `state` parse read 11.3 and
  11.6 ms after against 9.8 and 10.5 before, inside the 9.8 to 12.8 ms spread the Phase 364 baseline
  recorded for that cell; it is the collector (see that file).
