# A parse holds its nesting cap on a small stack — 2026-11-19 — Core Ultra 9 386H — Phase 663

Phase 663 asked whether `Json.parse` reaches its nesting cap before a small thread stack runs out, what one nesting
level costs on the stack in a Debug and a Release build, and, once the parse holds its open containers in the heap
instead of recursing, whether any parse got slower. The before figures were taken first, on the tree the phase was
cut from, before any change.

- **Machine:** Intel Core Ultra 9 386H, 16 logical processors, Windows 10.0.26300. Two other phases were building
  and testing on the machine throughout, so the wall-clock columns carry their load; the allocation columns and the
  depth probe do not depend on it.
- **.NET:** runtime 10.0.8, SDK 10.0.203.
- **Harnesses:** [`json-depth-phase-663.fsx`](json-depth-phase-663.fsx), beside this file, for the stack: every probe
  in its own process, because a stack overflow ends the process. [`json-parse-phase-616.fsx`](json-parse-phase-616.fsx)
  (Phase 616's, unchanged) and the wire benchmark's .NET leg (`benchmarks/run.ps1`, its `parse` column) for the time
  and allocation of a parse. For the comparison both builds of the wire benchmark were kept side by side and run
  alternately, before then after, so a change in the machine's load reaches both.
- **Trees:** before, `0acfd8d6`; after, the Phase 663 branch's final `Json.fs`.

## The stack, before

`json-depth-phase-663.fsx` in each build. "Lost" is the process ending with `0xC00000FD`, a stack overflow. The stack
per level is (1 MB − 256 KB) over the difference of the deepest documents that decode on the two stacks, which
cancels what the thread spends before the first level.

| build | shape | at the cap (512), 256 KB | past the cap (513), 256 KB | deepest decoded, 256 KB | deepest decoded, 1 MB | stack per level |
|---|---|---|---|---:|---:|---:|
| Release | arrays | lost | lost | 392 | 1,757 | 576 bytes |
| Release | objects | lost | lost | 336 | 1,506 | 672 bytes |
| Debug | arrays | lost | lost | 224 | 1,005 | 1,006 bytes |
| Debug | objects | lost | lost | 177 | 791 | 1,280 bytes |

The premise holds, and more strongly than the review that filed the phase measured (about 509 levels in a Debug build
of `0.41.0`): on a 256 KB thread the document AT the default cap ended the process in both builds, so the refusal the
cap promises was never reached there. The figure depends on the build by a factor of 1.75 to 1.9.

## The stack, after

| build | shape | at the cap (512), 256 KB | past the cap (513), 256 KB | deepest decoded, 256 KB and 1 MB (cap lifted) |
|---|---|---|---|---:|
| Release | arrays | decodes | refused at 512 | 100,000 (the probe's ceiling) |
| Release | objects | decodes | refused at 2,560 | 100,000 |
| Debug | arrays | decodes | refused at 512 | 100,000 |
| Debug | objects | decodes | refused at 2,560 | 100,000 |

A level costs no stack, so the probe's bisection finds nothing to bisect and no per-level figure is printed. The
refusal is the `Depth` breach at the bracket that passed the cap, the position the recursion reported where it
reached it.

## Reading it

- **Nothing a parse allocates grows past a few hundred bytes, and objects allocate less.** Every case allocates
  about 210 bytes more a call: the parse's open-container record for each level it reaches, made once a parse. The
  `members` case, 2,000 objects of five members, allocates 1.44 MB where it allocated 3.03 MB, because the record at a
  level keeps its lists and its member-name set for the next container opened there, where the recursion made a
  list, a closure and a set per object.
- **Time is within the noise of a loaded machine.** The same build's median moved by up to half between rounds over
  the day (before: `state` 0.90 to 1.40 ms over 24 rounds, `floats` 0.89 to 1.09 over 10, `literals` 0.18 to 0.30
  over 12), and an untouched column of the wire benchmark (`canon`, which no parse reaches) moved by up to 2.4 times
  between two runs of one build. Against that, `state` reads 5 %, `floats` 4 % and `literals` 15 % slower in the
  medians above, each inside the spread the before build showed across the day's rounds; `ints` reads level, and
  `op-stream` and `members` read 20 % and 43 % faster. Four intermediate shapes of the loop were measured the same
  way on the way to this one (a record per container instead of one per level, properties instead of fields, a
  dispatch per state instead of a value finished in the turn that starts it); none separated from the others or
  from the recursion by more than the spread of the rounds. The rounds are in the phase's run record; the medians
  above are the final shape's.
- **The falsifier held both ways.** Every timed case checks that its parse answers the value its text was rendered
  from before it is timed, and the wire benchmark checks its twenty output fingerprints against the pins first. The
  suite's new tests (`JsonReaderTests.fs`, "Json nesting on a small stack") ended the test process with a stack
  overflow on the tree before the change and pass after it.
