# Wire layer timing — 2026-10-05 — i7-9700 — Phase 373 (a float renders without the re-lay where the layouts agree)

Phase 373 asked whether `reLay`, which rebuilds every float under Fable into .NET's `"R"` layout, costs
a material share of a node render, and said to skip it where JavaScript's own `toString` already writes
the same characters only if it does. It also asked for parity vectors at the edges of that band and of
Phase 367's parse band, because Core's gate never compiles Fable (DECISIONS.md D55) and only those
vectors, run under node by the Fable consumer's parity leg, can see either branch. How to run and read
the tables: [`docs/wire-performance.md`](../../docs/wire-performance.md). The previous file:
[`2026-10-05-i7-9700-phase-372.md`](2026-10-05-i7-9700-phase-372.md).

- **Machine:** Intel Core i7-9700 @ 3.00 GHz, 8 logical processors, Windows 10.0.26200, mains power.
- **.NET:** SDK 10.0.401, Release build of `benchmarks/Fuaran.Core.Wire.Benchmarks`.
- **node:** v25.9.0. **Fable:** 5.0.0, from the toolchain of a checkout that owns one, compiling the
  harness to a scratch directory (D55). Each tree was compiled separately.
- **Trees:** before, fuaran-core `phase-373` at `42a4b8e` (Phase 372's landing); after, the same with this
  phase's `src/` change.
- **Command:** `pwsh ./benchmarks/run.ps1 -Runs 15 -NodeEntry <fable output>/Program.js`, twice for each
  tree; then the node renderers before and after in one process, interleaved (below).
- **Agreement:** in all four runs, the 20 case fingerprints were identical on .NET and node and matched
  the pins in `Corpus.fs` before anything was timed.

## The threshold, stated before the profile

MATERIAL meant both of these:

- (a) `reLay` is at least 5 per cent of the inclusive time of the node render of `floats`, `Json.render`
  and `Canon.render` each, in both profile runs;
- (b) the band covers most of the corpus's floats, so skipping the re-lay in it would move the render
  cell by more than its run-to-run spread.

5 per cent is Phase 367's figure, for its reasons: about the smallest change these tables resolve. The
falsifier was written with it: after the change, `reLay`'s samples must fall by roughly the in-band share
and the render cell must move by more than the interleaved A/A control.

## The band, and the change

Write a double's shortest round-trip digits as d1..dk with point position p, so the value is 0.d1..dk ×
10^p and dk is not zero. `reLay` recovers those digits from JS's string and sets its exponent to p - 1. It
writes fixed point exactly when p - 1 is in [-4, 16]: the digits with the point after p of them, or the
digits padded with p - k zeros when k <= p, or `0.` and -p zeros and the digits when p <= 0. ECMAScript's
`Number::toString` writes those same three shapes for every p in [-5, 21]. So for p in [-3, 17] the two
are the same characters, and a negative value is `-` and the same characters on both. p >= -3 is
|n| >= 1e-4 and p <= 17 is |n| < 1e17, compared as doubles: both bounds are shortest-digit values and
rounding is monotone, so no double on one side of a bound has shortest digits on the other.

Under `FABLE_COMPILER`, `FloatLayout.finite` now returns `n.toString()` when 1e-4 <= |n| < 1e17 and runs
`reLay` otherwise. On .NET it is `"R"`, unchanged. The band contains Phase 367's [2^53, 1e17), so 367's
separate parse-side shortcut, `FloatLayout.isFiniteLayout`, became the same test twice; it is removed and
the parser asks `FloatLayout.finite v = tok` again. The band now lives in one place.

## Every rendered float is byte-identical

- **node before, node after, .NET.** A pool of 2,387,628 doubles was built deterministically: every power
  of ten from 1e-30 to 1e30 and 2^52, 2^53 and 2^54, each with the 2,000 doubles either side; 400,000
  random bit patterns over the whole range; 400,000 values spread by exponent from 1e-8 to 1e20; short
  decimals k / 10^j; and 100,000 whole numbers below 1e18, all with both signs. 867,190 are in the band.
  For each, `FloatLayout.finite` and `Canon.canonicalFloat` were written out by the Fable output before
  the change, the Fable output after it, and .NET. The three listings are **byte-identical**.
- **The comparison can fail.** The after build with its band edited, compared against .NET:

  | band | differing doubles |
  |---|---:|
  | lower edge moved one double down, to the largest double below 1e-4 | 2 (`±0.00009999999999999999`) |
  | upper edge moved to include 1e17 | 2 (`±100000000000000000`) |
  | lower edge at 1e-5 | 41,612 |
  | upper edge at 1e18 | 216,952 |

- **The parser.** Phase 367's pool of 1,770,849 number inputs (590,283 tokens, bare, in an array and as a
  member value) gave byte-identical outcome listings on the Fable output before, the Fable output after
  and .NET: 1,286,982 accepted and 483,867 refused, the counts 367 recorded.

## Parity vectors at both edges of both bands

Twenty vectors were added to `ParityVectors.vectors`, and pinned on .NET in `ParityVectorTests.fs`:

- `floatLayout/band-*`: the adjacent doubles each side of 1e-4 and of 1e17, `-1e-4` and the negative
  below each edge, and a 17-digit value inside the band. A suite test holds each edge input to
  `Math.BitDecrement` / `Math.BitIncrement` of the edge, so the rows sit on the edges by construction.
- `jsonParse/*`: integer tokens at 2^53 - 1, 2^53, 2^53 + 1 (refused), 2^53 + 2 and its negative; the
  largest double below 1e17 written canonically (read) and with its exact digits (refused); and at 1e17,
  the integer spelling (refused, because the layout is `1E+17`), the exponent spelling (read) and the
  next double's integer spelling (refused).

**Which host runs them under node:** the Fable consumer's parity leg, fuaran-dotnet's
`tests/core-fable/core-fable.ps1`, which prints `ParityVectors.lines ()` on .NET and, transpiled, under
node and byte-compares the two; its cut-time run against the candidate packages is the one that sees
these rows first. For this phase the same program was compiled with Fable 5.0.0 against this tree in a
scratch project and run on both hosts: all 419 lines identical, the 20 new rows included. The same
program under node with its band edited, against the unedited run:

| band | rows that change |
|---|---|
| lower edge one double down | `floatLayout/band-below-1e-4`, `floatLayout/band-neg-below-1e-4` |
| upper edge to include 1e17 | `floatLayout/band-at-1e17`, `jsonParse/1e17-integer`, `jsonParse/1e17-exponent`, and the existing `canonicalFloat/e17` |
| upper edge at 1e18 | the four above, `floatLayout/band-above-1e17` and `jsonParse/above-1e17-integer` |

Before this phase only `canonicalFloat/e17` sat at either edge, and nothing sat at the lower one.

## What the figures say

- **The re-lay was two thirds of a node float render**, and three quarters of the corpus's floats are in
  the band where it is the identity. Skipping it there makes the node `floats` render and canonical
  render about 1.9 times faster in one process (after ÷ before 0.48 to 0.54, against a 1.04 to 1.08 A/A
  control), and moves the harness's node ÷ .NET ratio for them from about 6 to about 3.1.
- **On the other corpora the change is inside the method's resolution.** They carry one float per record
  or fewer; the forward runs read 1.00 to 1.11 and the reversed runs 0.80 and 0.95, all inside the slot
  bias the A/A row shows. Nothing is claimed for them.
- **What is left is the `E` layout.** The 2,500 floats outside the band are now about half of a node
  `floats` render. They are the values below 1e-4 and from 1e17 up, where the two layouts genuinely
  differ, so any further saving there is a cheaper re-lay rather than a skipped one. This phase does not
  attempt it.
- **.NET is untouched**: the same `"R"` call, and the cells moved only with the machine.
