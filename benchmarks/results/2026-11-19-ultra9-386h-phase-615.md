# One walk for the validator and for an op's change set — 2026-11-19 — Core Ultra 9 386H — Phase 615

Phase 615 asked whether `Validator.runAll` pays for each `perNode` family building its own preorder, and whether
`Propagation.changedForOp` pays for walking the tree several times per op; if they do, for one shared preorder per
`runAllTagged` and for `seedsForOp` / `changedForOp` overloads that take a held `Tree.NodeIndex`. The review that
filed it estimated the cost by reading the code and did not know how often the UI tier reaches either call. This
file measures both, and answers that question.

**Verdict: no code changes.** The walks are a real share of each call on a synthetic 5,000-node tree, but no
production path of `fuaran-dotnet` reaches either call per render or per op, so the threshold below is not met.
The figures stay here so that if a per-render or per-op caller appears, the case for the change is already measured.

## The threshold, written before the baseline was taken

The phase changes code only if BOTH of these hold:

1. **A caller pays it.** `fuaran-dotnet` reaches `Validator.runAll` / `runAllTagged` over a registry of
   `perNode` families, or `Propagation.changedForOp` / `dirtyFromOp`, at least once per render or once per
   applied op on a production path (not a test, not a certification tool run once per declaration).
2. **The walk is a material share of the call.** At 5,000 nodes, the saving a shared walk can buy is at least
   25 % of the call's mean time AND at least 1 ms per call. The saving is measured below as the difference between
   the shipped call and a one-walk equivalent built in the harness from the same public pieces.

If either fails, the result is recorded here and no source changes.

## How often `fuaran-dotnet` reaches the two calls

Read from `fuaran-dotnet` at `78e9123e` (its `main` on 2026-11-19), production sources only (tests, samples and
build output excluded):

- **`Validator.runAll` / `runAllTagged`: zero times per render, zero per op.** The one production call site is
  the generated `runValidator` scaffold in `src/Fuaran.UI/Generated.fs`, and nothing calls it. The tier's own
  pre-emit validation (`PreEmitValidate.validate`) is its own walk, not a Core registry. Where it is wrapped as a
  Core `RuleFamily` (`PreEmitValidate.ruleFamily`), the registry holds that ONE family, built as a record literal
  rather than with `perNode`. It is used by the recipe certification tool, once per checked binding, and not on
  the render path. A one-family registry walks the tree once already. The merge gate in
  `Fuaran.UI.OpStream.Dag.Merge` runs the caller's validator and uses Core only for `introducedDefects` and
  `verdict`, which do not walk the tree.
- **`Propagation.changedForOp` / `dirtyFromOp`: zero times per render, zero per op.** No production source calls
  either. The renderer's binding graph (`Fuaran.UI.Renderer.Core/BindingGraph.fs`) calls
  `Propagation.dirtyFromChangedIds` over a dependency map it holds. That closure walks no tree and is not in
  this phase's scope.

So condition 1 fails for both halves. Condition 2 holds for both, as the tables show.

## What the figures say

- **The validator.** At 5,021 nodes, `runAll` over 30 families takes 6.35 ms and allocates 18.7 MB. The same 30
  rule bodies over one preorder take 2.42 ms and allocate 8.6 MB. The 29 extra preorders account for about
  2.5 ms and 13.9 MB of that difference (29 × one preorder's 0.085 ms and 480 KB). The rest is the walker
  stamping each family's findings. A shared walk would save about 39 % of the call, so condition 2 holds.
- **The change set.** At 5,021 nodes, `changedForOp` takes 11.7 ms and allocates 33.6 MB per op, for an update
  and an insert alike. The two id-to-node maps `seedsForOp` builds and the `Tree.ids` of the post-edit tree take
  3.75 ms and 14.1 MB. A held `Tree.NodeIndex` would remove those walks, about 32 % of the call, so condition 2
  holds. The dependency map, 1.56 ms, stays without a held map as well. The per-node diff of child lists and read
  sets is inherent to the seed set the proofs state. `touchedBy` over an `UpdateNode` does not walk at all.
- **No gen2 collection** occurred in any case at either size.

## Why the validator half would not be additive

The shard classes the phase additive ("new overloads"). That holds for the propagation half: `seedsForOp` /
`changedForOp` overloads over a held `Tree.NodeIndex` would be new entry points. It does not hold for the
validator half. A `RuleFamily` is `{ Id; Run }`, and `Run` is an opaque function of the witness and the root, so
`runAllTagged` cannot tell a `perNode` family from any other. It can share one preorder only if the record learns
which families are per-node. A new field on that public record breaks every full record literal (FS0764), and
`fuaran-dotnet` builds one (`PreEmitValidate.ruleFamily`). Memoising the preorder per root inside `perNode` would
avoid the field but would add hidden shared state to a pure function. So if a per-render caller ever makes the
validator half worth building, it is a breaking change to `RuleFamily` and needs its own decision. It cannot
ride a patch slot.

## What would reopen this

A production path in `fuaran-dotnet`, or any other consumer, that calls `Validator.runAll` over many `perNode`
families per render, or `changedForOp` / `dirtyFromOp` per applied op. If that happens, the table above is the
before figure, and the bounds measured here (about 39 % and 32 % at 5,000 nodes) are what the change can buy.
