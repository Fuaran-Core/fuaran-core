# An indexed apply entry — 2026-11-14 — i7-8650U — Phase 659

Phase 659 asked for an apply entry that reads a `Tree.Index`, so that a caller holding a fresh index pays the op and
not the tree, and for a progressive build at 1,000 and 10,000 nodes, before and after, by the harness Phase 607
committed. This file is that measurement. The before figures were taken first, on the tree Phase 607 left, before any
change; the after figures on this phase's tree.

- **Machine:** Intel Core i7-8650U @ 1.90 GHz, 8 logical processors, Windows 10.0.26300, mains power. Other sessions
  were running on the machine throughout, so the time columns are noisy; the allocation column is the measure the
  phase is about, and it does not depend on load.
- **.NET:** SDK 10.0.203, Release build of the libraries the harness references.
- **Harness:** [`tree-lookups.fsx`](tree-lookups.fsx), beside this file, run as its header says, one case at one size
  per process (`dotnet fsi --optimize+ benchmarks/results/tree-lookups.fsx -- <case> <size>`). This phase adds three
  cases to it: `insert-indexed` (607's insert through `IndexedTree.apply`, over an index built outside the timed
  closure), `progressive` and `progressive-indexed`.
- **The progressive build:** `size / 5` phases built under a bare root one node per op, in `tree size`'s shape: an
  epoch before every fiftieth phase, each phase followed by its four tasks, so 1,005 nodes for `1000` and 10,041 for
  `10000`. `progressive` applies each op through `Ops.apply`; `progressive-indexed` makes the `IndexedTree` of the bare
  root inside the timed closure and applies each op through `IndexedTree.apply`. Each case checks the tree it reached
  before it is timed.
- **Trees:** before, `phase-659` at `c7d3013` (Phase 607 landed); after, the branch at `5984e33`.
- **Columns:** as 607's: wall time per call in milliseconds (mean, median, p95), bytes the calling thread allocated per
  call, and generation-2 collections per call. A progressive row's call is the whole build.

## Reading it

- **A progressive build of 10,041 nodes through `IndexedTree.apply` allocates 223 MB, where the same build through
  `Ops.apply` allocates 49.1 GB, and takes a median 0.21 s where it took 48 s.** At 1,005 nodes it is 17.0 MB against
  384 MB. Ten times the nodes cost 13.1 times the bytes through the indexed entry, which is N log N (10 × log 10,041 /
  log 1,005 is 13.3). The per-insert figure grows from 16.9 KB to 22.2 KB: the depth of the persistent maps the index
  is, and the child lists of the path's nodes, which every insert rebuilds.
- **One insert into a 20,081-node tree allocates 40.6 KB through `IndexedTree.apply` and 21.7 MB through `Ops.apply`.**
  What remains of `Ops.apply`'s cost is its walks: the base check (`Tree.wellFormed`, about 20 MB of it by Phase 607's
  reading), the duplicate check and the parent lookup.
- **`Ops.apply` itself allocates less than before** (21.7 MB against 28.2 MB on the insert, 49.1 GB against 55.5 GB on
  the 10,041-node build). The edit's rewrite built its `UnknownNode` refusal eagerly, enumerating every id of the tree
  on every accepted edit; it now builds it only when the rewrite misses (D258.3).
- **The `rebind` change is the indexed entry's last large cost.** Before it, the indexed build of 10,041 nodes
  allocated 868 MB (and 44.7 MB at 1,005, a ratio of 19.4): every re-indexed ancestor withdrew and re-installed a
  `ParentOf` entry per child, so the root and each epoch cost a map write per child on every insert. That figure was
  measured at `30f7715` and is not in the table, which is the tree that ships.
