# Rendering a date or an instant — 2026-11-19 — Core Ultra 9 386H — Phase 611

Phase 611 asked whether `TemporalText.dateText` and `TemporalText.instantText`, which built their text by padding
each part to a string and concatenating the parts, cost the per-row paths that call them a material share of their
allocation, and, if they did, to render each into one `char[]` and one string. The shard estimated the cost from
reading the code; this file is the measurement, taken before any change, and the same measurement after it.

- **Machine:** Intel Core Ultra 9 386H, 16 logical processors, Windows 10.0.26300, mains power.
- **.NET:** SDK 10.0.203 (runtime 10.0.8), Release build of the column package the harness references.
- **Harness:** [`temporal-text-phase-611.fsx`](temporal-text-phase-611.fsx), beside this file, run as its header says
  (`dotnet fsi --optimize+ benchmarks/results/temporal-text-phase-611.fsx`). Each case runs in its own process. The
  input is built outside the timed closure. Each case warms up for three seconds of wall-clock time, then samples
  until a ten-second budget is spent (at least five samples, at most 2,000). Every case checks its answer before it
  is timed: the rendered texts against .NET's own `DateTime` formatting, the cell reads against the same.
- **Load:** both runs were taken holding a shared benchmark lock, so no other measured run was alongside them; builds
  by other sessions may still have been running. The allocated bytes and gen2 counts do not depend on load and are
  the primary evidence.
- **Trees:** before, `phase-611` at `4b60cdb3`; after, the same branch at `4d07da19`, this phase's change.
- **Columns:** wall time per call in milliseconds (mean, median, p95), the bytes the calling thread allocated per
  call and per row, and generation-2 collections per call. One call renders or reads all 100,000 rows once.

## The cases

- **`dateText`** over 100,000 days spread across `0001-01-01`..`9999-12-31`.
- **`instantText`** over 100,000 instants at seconds, milliseconds and nanoseconds: a second anywhere in that range,
  a fraction anywhere in the unit's range, one in ten of them zero.
- **`Column.cell`** read at every row of a null-free 100,000-row date column and millisecond timestamp column: the
  per-row read every consumer of a temporal column goes through.
- **A group-by on a date key in the compute layer:** 100,000 rows, 1,000 distinct days, counting a float column,
  through its `evalPipeline`. The compute assembly is loaded by path (the harness's `FUARAN_COMPUTE_DATAFRAME_DLL`)
  and runs against the column package built in this tree. See "The group-by" below for which build that was.

## Was it material?

The threshold was written down before the baseline run: MATERIAL means the bytes the change would remove (what the
render allocates, less the one result string it must return) are at least 5 % of the bytes a named per-row path
allocates, or the change moves the path's gen2 count.

The result string of a date is 48 bytes on 64-bit .NET (a 10-character string), of an instant 64 to 80 bytes.

| path | bytes / row | render's bytes / row | removable bytes / row | share |
|---|---:|---:|---:|---:|
| `Column.cell`, date | 211.7 | 179.7 | 131.7 | 62 % |
| `Column.cell`, timestamp_ms | 454.7 | 422.7 | about 350 | 77 % |

The cost was material on the named path, so the change went ahead.

## After

The change as landed: a day in the canonical range renders its ten characters into one `char[10]`, written digit by
digit from the civil parts the date accessors already share, and becomes one string. An instant in range writes its
date, its time of day and its fraction's significant digits (the unit's width less its trailing zeros) into one
array of exactly its length. A day, a second of the day or a fraction outside the canonical range keeps the padded
text it always had, so no rendered byte moves anywhere; tests hold both renders against the padded form at every
unit, over drawn instants and every edge.

## Reading it

- **`dateText` allocates 96 bytes a call where it allocated 180 (−47 %)**: the `char[10]` and the string, 48 bytes
  each, where the old form made a string per part, a padded copy of each and the joins.
- **`instantText` allocates 128 to 171 bytes a call where it allocated 364 to 468 (−63 % to −65 %)**: the array and
  the string, each sized to the text.
- **A cell read of a date column allocates 128 bytes a row where it allocated 212 (−40 %), and of a millisecond
  timestamp column 174 where it allocated 455 (−62 %).** The rest is the cell and the result string.
- **Timings:** each render's median roughly halves (`dateText` 4.49 to 2.57 ms per 100,000; `instantText` at
  milliseconds 10.85 to 4.63 ms), and the cell reads follow (5.26 to 3.33 ms, 11.98 to 5.47 ms).
- **The group-by.** The compute assembly this harness loaded was the one built on this machine, which predates the
  compute layer's change that codes a date key in range by its day count rather than by its text (made 2026-11-08,
  after the build). That build renders every row's key, so its allocation halves with this change (191.9 to 107.4
  bytes a row). The compute layer as it stands now renders a date key's text only once per output group, so on it
  this change saves only the 1,000 renders of the keys it outputs; the per-row figures above for `Column.cell`, and
  the compute layer's own per-row reads of temporal cells, are where the change pays there.
- **The single buffer does not use `String.Create` or a span:** the same code compiles under Fable, as the rest of
  the column package does, and a `char[]` plus `String(char[])` is the form the package's digest hex already uses.
- **No byte moved:** the column, temporal and proof-oracle suites pass unchanged, including the walk of every
  canonical date and the differential against the proof's model of the text, and the new tests fail when a fraction
  digit is written wrong.
