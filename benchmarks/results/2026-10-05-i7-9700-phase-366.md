# Wire layer timing — 2026-10-05 — i7-9700 — Phase 366 (the string parser reads by runs)

Phase 366 changed how the parser reads a string. `parseString` (inside `Json.parseDetailedWithPolicy`)
appended each character to a builder through a check of its surrogate pairing. It now walks each
escape-free stretch up to the next `"` or `\`, checking the pairing of each unit as it passes, and takes
the stretch whole: one `Substring` when the closing quote ends the first stretch (no builder at all), or
one ranged `Append` around an escape. Every refusal keeps its kind, message and position. The "before"
is the tree this phase started from, which already holds Phase 365's escape fast path; the earlier
baselines are [`2026-10-04-i7-9700-phase-364.md`](2026-10-04-i7-9700-phase-364.md) and
[`2026-10-05-i7-9700-phase-365.md`](2026-10-05-i7-9700-phase-365.md). How to run and read the tables:
[`docs/wire-performance.md`](../../docs/wire-performance.md).

- **Machine:** Intel Core i7-9700 @ 3.00 GHz, 8 logical processors, Windows 10.0.26200, mains power.
- **.NET:** SDK 10.0.401, Release build of `benchmarks/Fuaran.Core.Wire.Benchmarks`.
- **node:** v25.9.0. **Fable:** 5.0.0 (fable-library-js 5.0.0), from the toolchain of a checkout that
  owns one, compiling the harness to a scratch directory (DECISIONS.md D55). Each tree was compiled
  separately.
- **Trees:** before, fuaran-core `phase-366` at `f2eea75` (no change to `src/`); after, the same branch
  with this phase's `src/` change.
- **Command:** `pwsh ./benchmarks/run.ps1 -Runs 15 -NodeEntry <fable output>/Program.js`, run twice back
  to back for each tree, then a third before/after pair interleaved as a drift check.
- **Agreement:** in all six runs, the 16 case fingerprints were identical on .NET and node and matched
  the pins in `Corpus.fs` before anything was timed. The parser's output did not change.

Figures are the median of 15 samples, in milliseconds per call. Only `parse` runs changed code; the
escape, render and canon columns are the same code before and after and show the machine's drift.

## The drift check: a third pair, before then after, back to back

The unchanged columns moved between the first two pairs (node render on `state` read 6.25 before and
5.37 after, on the same code), so a third pair was run interleaved. Parse, before → after:

|---|---:|---:|

| op-stream | 2.062 → 1.555 | 7.124 → 2.750 |

`escape-heavy` 0.373 → 0.493, node render on `escape-heavy` 2.250 → 2.625, the same code), so its
`escape-heavy` parse reading is drift, not a regression: the first two pairs put that cell level.

## The refusals did not move

- **.NET**, in the suite (`StringParseRunTests.fs`): the parser before this phase is kept as a
  one-unit-at-a-time reference reader, and production is compared with it over every sequence of up to
  four tokens from a run-boundary alphabet (raw stretches, raw high and low surrogate halves, every
  short escape, `\u` escapes of a BMP character and of each half, every malformed escape, a bare quote),
  each closed and left open: 177,482 inputs, every outcome compared as decoded string or refusal kind,
  message and position. Nineteen named inputs state each refusal's position outright at the start, the
  middle and the end of a run and across a run/escape boundary. Two broken readers (one forgets a
  pending high surrogate at an escape, one loses a run's last unit) are red in the suite; and two
  deliberate breaks of production itself (the first run copied one unit short; the pairing state reset
  at an escape) were each shown red against it, then reverted.
- **node**: the Fable output of the tree before and after were run side by side over the same token
  sweep, 200,000 random strings (alone, as an object key and as an array item) and every UTF-16 code
  unit raw, inside a run and `\u`-escaped: 674,090 inputs, 456,928 of them refusals, no difference in
  value, kind, message or position. The same check with every after-position shifted by one was red on
  all 456,928 refusals.

## What the figures say

- **Parse is two to three and a half times faster under node** on every corpus but `escape-heavy`
  (each figure the faster "before" over the slower "after", runs 1 and 2): `escape-free` 3.5 times,
  `op-stream` 2.9 times, `state` 3.0 times. A string with no escape is now one `Substring`.
- **On .NET, parse allocates 41 to 57 per cent less on those corpora**, which is where its time went
  (Phase 364: the `state` parse is mostly the collector). `escape-free` parse is 2.5 times faster;
  `op-stream` 2.0 times; `state` 1.5 times in the first two pairs and 1.09 in the drift pair, the cell
  that moves most with the collector.
- **`escape-heavy` is level**, within the spread, on both hosts: its strings are mostly escapes, so the
  runs are short and the builder is still needed. Its allocation is unchanged to within 208 bytes per
  call (the builder now grows by ranged appends).
- **The node ÷ .NET parse ratio fell** from 2.9–4.8 before to 2.0–3.4 after on `escape-free`,
  `escape-heavy` and `op-stream`; on `state` it fell from about one (0.94 and 1.01) to about a half.
