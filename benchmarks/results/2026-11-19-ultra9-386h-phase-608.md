# Column fill's mask and pair array — 2026-11-19 — Core Ultra 9 386H — Phase 608

Phase 608 asked whether a column build's throw-away `bool` mask (allocated by `TypeOps.fill` for every column and
discarded when no row is absent) and a timestamp column's struct-pair array cost the codec's decode and the compute
layer's per-group aggregates a material share of their allocation, and, if they did, to allocate the mask only on
the first absent row and fill a timestamp column's two arrays directly. The shard estimated the cost from reading
the code; this file is the measurement, taken before any change, and the same measurement after it.

- **Machine:** Intel Core Ultra 9 386H, 16 logical processors, Windows 10.0.26300, mains power.
- **.NET:** SDK 10.0.203 (runtime 10.0.8), Release build of the column package the harness references.
- **Harness:** [`column-fill-phase-608.fsx`](column-fill-phase-608.fsx), beside this file, run as its header says
  (`dotnet fsi --optimize+ benchmarks/results/column-fill-phase-608.fsx`). Each case runs in its own process. The
  input is built outside the timed closure. Each case warms up for three seconds of wall-clock time, then samples
  until a ten-second budget is spent (at least five samples, at most 2,000). Every case checks its own answer
  before it is timed.
- **Load:** other benchmark runs were serialised against these by a lock on this machine, so the timings were taken
  with no other measured run alongside; builds by other sessions may still have been running. The allocated bytes
  and gen2 counts do not depend on load and are the primary evidence.
- **Trees:** before, `phase-608` at `0feef93`; after, the same tree with this phase's `src/` change.
- **Columns:** wall time per call in milliseconds (mean, median, p95), the bytes the calling thread allocated per
  call, and generation-2 collections per call.

## The cases

- **`ColumnCodec.decode`** of a one-column embedded table of 100,000 rows with no absent row: a `float` column, and a
  millisecond `timestamp` column (the row whose storage is two vectors).
- **`aggCells`** is the compute layer's adapter for every deferred group and pivot aggregate: `Column.ofCells` over
  one group's cells, then `Column.aggregate`. The harness runs that pair over 10,000 groups of ten cells (100,000
  rows): `Sum` over a `float` column, and `Max` over a millisecond `timestamp` column. One call is all 10,000 groups.

## Was it material?

The threshold was written down before the baseline run: MATERIAL means the bytes the change removes (the mask,
`n + 24` bytes rounded up to 8; for a timestamp column also the pair array, `16n + 24`) are at least 5 % of the
bytes the named call allocates on either named path, or the change moves the call's gen2 count.

| case | bytes / call | removable bytes / call | share |
|---|---:|---:|---:|
| decode, float, 100,000 rows | 25,492,147 | 100,024 | 0.4 % |
| decode, timestamp_ms, 100,000 rows | 47,100,588 | 1,700,048 | 3.6 % |
| aggCells Sum, float, 10,000 groups | 5,120,000 | 400,000 (40 per group) | 7.8 % |
| aggCells Max, timestamp_ms, 10,000 groups | 122,256,320 | 2,240,000 (224 per group) | 1.8 % |

The per-group `Sum` crosses the threshold: a group of ten cells allocates 512 bytes, and 40 of them are a mask it
throws away. So the change went ahead. The decode figures say the shard's framing was wrong for decode: at 100,000
rows the mask is under half a per cent of a float column's decode, which is dominated by the parse.

## After

The change as landed: `TypeOps.fill` allocates the mask at the first absent row, filling the rows before it as
present, and answers `AllValid` holding no array when no row is absent; a one-vector type's storage is its array,
written by the walk directly; and a timestamp row's storage writes each pair straight into its two vectors, so no
pair array is built and copied out.

| case | rows | samples | mean ms | median ms | p95 ms | allocated bytes / call | gen2 / call |
|---|---:|---:|---:|---:|---:|---:|---:|
| ColumnCodec.decode (float, null-free) | 100000 | 620 | 16.1371 | 10.8789 | 35.8335 | 25392077 | 0.131 |
| ColumnCodec.decode (timestamp_ms, null-free) | 100000 | 402 | 24.9052 | 18.2310 | 41.6144 | 45400311 | 0.144 |

## Reading it

- **The per-group `Sum` allocates 4.40 MB where it allocated 5.12 MB (−14 %): 440 bytes a group where it was 512.**
  That is more than the 40-byte mask the threshold counted, because the old fill also wrapped the mask in a vector
  before `Validity.ofVector` found every bit set and dropped it.
- **A first cut of the change saved only 8 bytes a group there** (5.04 MB). It wrote every type's rows through a
  storage object, and that object cost about what the mask had. The landed form keeps a one-vector type's array as
  its storage, with no object and no virtual call per row, and gives only the timestamp's two vectors a storage
  object, which replaces the pair array.
- **The timestamp decode allocates 45.4 MB where it allocated 47.1 MB (−1.70 MB, −3.6 %), and its gen2 count per
  call falls from 0.178 to 0.144.** The 1.6 MB pair array and the 100 KB mask were both on the large object heap.
- **The float decode allocates 0.1 MB less (−0.4 %), the 100 KB mask; its gen2 count does not move** (0.128 to
  0.131 is within run-to-run noise). Decode is dominated by the parse and the codec's own lists, which this phase
  does not touch.
- **The per-group timestamp `Max` allocates 2.0 MB less (−1.6 %)**; it is dominated by the aggregate itself.
- **Timings:** the decode and float aggregate medians are within run-to-run noise. The timestamp aggregate's median
  fell from 40.9 ms to 27.7 ms; a run between the two, of the first cut, read 28.4 ms, so part of the before figure
  is likely load from builds running alongside, and this file does not claim that fall.
- **No byte moved:** the suite's codec, conformance and validity tests pass unchanged, and a new test pins the mask
  at every position of the first absent row, at every column type, through `Column.ofCells` and decode. Removing the
  back-fill of the earlier rows makes it fail.
