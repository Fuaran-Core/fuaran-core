# Tree lookups and the graft check — 2026-11-14 — i7-8650U — Phase 607

Phase 607 asked whether the tree's lookups and an insert's duplicate check cost an op-applying replay a material
share of its allocation, and, if they did, to make the lookups stop at their first preorder match and the duplicate
check key the graft rather than the whole tree. The shard estimated the cost from reading the code; this file is the
measurement, taken before any change, and the same measurement after it.

- **Machine:** Intel Core i7-8650U @ 1.90 GHz, 8 logical processors, Windows 10.0.26300, mains power.
- **.NET:** SDK 10.0.203 (runtime 10.0.15), Release build of the libraries the harness references.
- **Harness:** [`tree-lookups.fsx`](tree-lookups.fsx), beside this file, run as its header says
  (`dotnet fsi --optimize+ benchmarks/results/tree-lookups.fsx`). Each case at each size runs in its own process.
  The input is built outside the timed closure. Each case warms up for a fixed wall-clock time (three seconds, or
  one second for a replay), then samples until a ten-second budget is spent (twenty for a replay), at least five
  samples, and three for the 8,800-op replay, whose every call takes minutes. Every case checks its own answer
  before it is timed.
- **Trees:** before, `phase-607` at `f9838d9`; after, the same tree with this phase's `src/` change.
- **Columns:** wall time per call in milliseconds (mean, median, p95), the bytes the calling thread allocated per
  call, and generation-2 collections per call.

## Was it material?

The shard set no threshold, and none was written down before the run. The one applied to the baseline: MATERIAL
means the lookups and the graft check together are at least a quarter of the bytes
`Ops.apply (InsertChild …)` allocates on a 20,000-node tree. They were 24.3 MB of 48.6 MB: `graftWellFormed`
20.0 MB, and the insert's parent `tryFind` 1.9 MB. The other half is `Tree.wellFormed`, which every entry
of `Ops.apply` runs over the whole base tree (below). So the cost was material and the change went ahead.

## The trees

`nodes` is the tree's node count. The lookup and insert trees are roadmap-shaped: a root, epochs of 50 phases,
each phase with four tasks. The lookups look for a task in the middle phase, and the insert appends a task under
the last phase. The replay cases are a GENERATED store, not a real one: `size` ops on a linear DAG under
`Dag.tryReplayTo`, each applied by `Ops.apply` under a contained scope. Two ops in three insert a phase with one
task under one of sixty epochs. The third rewrites an earlier phase's value. `nodes` there is the tree the head
replays to.

## Reading it

- **The insert on a 20,081-node tree allocates 28.2 MB where it allocated 48.6 MB (−42 %), and its median falls from
  205 ms to 79 ms.** The graft check fell from 20.0 MB to 0.77 MB: it keys the graft (one id) and walks the tree
  once, testing membership. The parent lookup fell from 1.9 MB to 0.39 MB: it stops at the parent. The lookups
  still allocate in proportion to the nodes they visit, because the explicit stack is an immutable list, but they
  no longer allocate for the nodes they do not visit.
- **The 8,800-op generated replay allocates 56.8 GB where it allocated 86.6 GB (−34 %).** Its median falls from
  307 s to 273 s, a smaller fall than the 2,000-op replay's (19.6 s to 6.5 s). Three samples of a five-minute call
  under GC pressure are noisy: the two p95 columns, each the slowest of three, are within half a per cent of each
  other. The allocation figure is the steadier measure, and it is the one the phase is about.
- **What remains is `Tree.wellFormed`, run once per `Ops.apply` over the whole base tree.** `Ops.apply` refuses
  an id-repeating base (`DuplicateId`) before every step. It does that through `Tree.wellFormed`, which keys every
  id of the tree into an immutable `Set`. That is the same keying the old graft check did, so it is about 20 MB of
  the remaining 28.2 MB at 20,081 nodes. This is an inference from the before table's `graftWellFormed` row, which
  runs the same scan over the same tree, not a separate measurement. Phase 607 does not name that check, and
  changing it changes what an entry verifies, so it is left as it is, and reported. It is the next lever on replay
  allocation: a replay re-proves, at every op, a uniqueness that the previous op preserved.

## The fuaran side's store

The acceptance names `Dag.tryReplayTo` over the fuaran side's roadmap store. That store is replayed by an engine
that consumes a released `Fuaran.Core` and its own op vocabulary, neither of which this repository builds. A before
and after over it needs that engine rebuilt against this tree. The generated store above stands in for it, at the
op count the review cited.
