# Exact-decimal arithmetic — 2026-11-19 — Core Ultra 9 386H — Phase 613

Phase 613 asked whether exact-decimal arithmetic, which built a string per digit of a sum, re-read the canonical
texts an aggregate had already admitted, and made some twenty strings per `DecimalText.add`, cost the paths that
call it a material share of their allocation, and, if it did, to work over the canonical text in place. The shard
estimated the cost from reading the code; this file is the measurement, taken before any change, and the same
measurement after it.

## Was it material?

The threshold was written down before the baseline run: MATERIAL means that `Column.aggregate Sum` over a
100,000-row null-free decimal column allocates at least 200 bytes a row (the one fresh running-total text a row
needs is some 40 to 60 bytes, so 200 is about four short strings more than that), or collects generation 2 in more
than one call in ten, or that `DecimalText.add` over two short canonical texts allocates at least 200 bytes a call.

The named path allocated 1,247.8 bytes a row before the change, and `add` 863 bytes a call. The cost was material,
so the change went ahead.

## The run

- **Machine:** Intel Core Ultra 9 386H, 16 logical processors, Windows 10.0.26300, mains power.
- **.NET:** SDK 10.0.203 (runtime 10.0.8), Release build of the column package the harness references.
- **Harness:** [`decimal-sum-phase-613.fsx`](decimal-sum-phase-613.fsx), beside this file, run as its header says
  (`dotnet fsi --optimize+ benchmarks/results/decimal-sum-phase-613.fsx`). Each case runs in its own process. The
  input is built outside the timed closure. Each case warms up for three seconds of wall-clock time, then samples
  until a ten-second budget is spent (at least five samples, at most 2,000). Every case checks its answer before it
  is timed, against one computed in exact integer arithmetic and rendered canonically by the harness itself.
- **Load:** every run was taken holding a shared benchmark lock, so no other measured run was alongside it; builds
  by other sessions may still have been running. The allocated bytes and gen2 counts do not depend on load and are
  the primary evidence.
- **Columns:** wall time per call in milliseconds (mean, median, p95), the bytes the calling thread allocated per
  call and per row, and generation-2 collections per call. One `Sum`, `Mean` or `Max` call aggregates all 100,000
  rows once; one `add` sample is 1,000 calls, so its bytes per row are bytes per call.

## The cases

- **`add (short)`**: `DecimalText.add` over 64 fixed pairs of canonical texts between `-1000` and `1000` with up to
  three fraction digits, of both signs.
- **`add (40 digits)`**: the same over pairs of some 40 digits at a scale of 12.
- **`Sum (decimal)`**: `Column.aggregate Sum` over 100,000 canonical decimals of the short shape. The acceptance's
  named path.
- **`Mean (decimal)`**: `Column.aggregate Mean` over the same column, which reads each admitted text as a float.
- **`Max (decimal)`**: `Column.aggregate Max` over the same column, which compares each row with the greatest so far.

## Reading it

- **The named path: `Sum` over the 100,000-row decimal column allocates 94.6 bytes a row where it allocated
  1,247.8**, 9.5 MB a call where 124.8 MB, and its median falls from 28.57 ms to 7.12 ms. What a row allocates now
  is the new running total: one `char[]` laid out as the sum's text, and the one string read out of it. Before,
  each row's admitted text was parsed again, both operands were padded, split and trimmed into some twenty strings,
  and the sum's digits were rendered one string per digit.
- **`DecimalText.add`** allocates 160 bytes a call where it allocated 863 over the short texts (median 0.151 µs to
  0.045 µs a call), and 260 where 1,656 over the 40-digit ones. Its operands are canonical here, so `tryCanonical`
  answers each as itself after a scan, and the two options around them are what remains beside the sum.
- **`Mean`**, which reads each admitted text as a float, allocates 24.0 bytes a row where it allocated 590.9
  (median 14.03 ms to 4.54 ms): the admission no longer rewrites a canonical text, and neither does `tryToFloat`
  before it parses one.
- **`Max`** allocates 104.0 bytes a row where it allocated 1,330.0 (median 23.53 ms to 4.41 ms): the comparison
  reads the two canonical texts in place, place by place, where it padded and concatenated both. The options the
  cell comparison wraps around each text are what remain.
- **Gen2** stays at or near zero on every case, before and after.
- **No answer moved.** The `proofs/DecimalText.fst` oracle differential over its generated pool of texts and pairs,
  canonical and not, passes unchanged; new tests hold `isCanonical` to the model's fixed point over the pool and
  the edge texts (`-0`, `00`, `1.10`), a canonical text to being answered as itself, `Sum` over 3,000 canonical
  cells of mixed sign and scale to the model's sum folded over the same texts, and the `Sum` path to under 200
  bytes a row. With the shape scan made to accept `-0`, the differential and the new fixed-point test both fail.
