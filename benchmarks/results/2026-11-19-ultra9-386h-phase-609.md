# A digest copies its input once — 2026-11-19 — Core Ultra 9 386H — Phase 609

Phase 609 asked whether `Hash.sha256Hex` pays for copying its input more than once on the way to a digest, and, if
it does, for an encoder that sizes one exact array and a compression that reads blocks straight from the input. The
review that filed it estimated the cost by reading the code; this file measures it. The before figures were taken
first, on the tree the phase was cut from, before any change.

- **Machine:** Intel Core Ultra 9 386H, 16 logical processors, Windows 10.0.26300. Other campaign workers were
  building on the machine; the timed runs were taken under the campaign's benchmark lock, so no other worker was
  timing at the same moment, but builds were not excluded. The allocation column is the measure the phase is about,
  and it does not depend on load.
- **.NET:** runtime 10.0.8, SDK 10.0.203, Release build of `Fuaran.Core.Text`.
- **Harness:** [`digest-phase-609.fsx`](digest-phase-609.fsx), beside this file, run as its header says, one case at
  one size per process. It checks every answer against the platform encoder and digest before it times anything.
- **Cases:** `Hash.utf8Bytes` over a string of `size` UTF-16 units; `Hash.sha256HexOfBytes` over `size` bytes;
  `Hash.sha256Hex` over a string of `size` units (the two composed). The string is mostly ASCII with a two-byte unit,
  a three-byte unit and a surrogate pair in every seventeen units, so `size` units encode to about 1.29 × `size`
  bytes.
- **Trees:** before, `0feef93f` (the 0.44.1 slot opened); after, `12b46b0f`.
- **Columns:** Phase 607's: wall time per call in milliseconds (mean, median, p95), bytes the calling thread
  allocated per call, and generation-2 collections per call.

## Reading it

- **The cost was real, and it was allocation.** Before, `sha256Hex` over a million mixed units (1.36 MB of UTF-8)
  allocated 9.63 MB a call, seven times the bytes it hashes, and drove a generation-2 collection every seven calls.
  The encoder grew a `ResizeArray<byte>` and copied it out (5.55 MB for 1.36 MB of output), and the compression
  copied the whole message into a second `ResizeArray<byte>` to pad it (3.15 MB for 1 MB of input). After, the call
  allocates 1.36 MB — the encoded bytes and nothing else of size — and a gen2 every thirty calls.
- **`sha256HexOfBytes` now allocates a constant 728 bytes at every size**: the 256-byte schedule, the eight state
  words, the tail scratch, the `char[64]` and the string. Before it allocated 3,064 bytes at 64 bytes of input and
  three times its input above that. At 64 units `sha256Hex` allocates 832 bytes where it allocated 3,648.
- **`utf8Bytes` allocates its output exactly**: 1,357,147 bytes for a 1,356,979-byte encoding (168 bytes over it, the array header among them),
  where it allocated 4.1 times that. Its median time at a million units fell from 2.03 to 1.35 ms.
- **Time at large sizes is the compression, and it did not move beyond the noise.** `sha256HexOfBytes` over 1 MB has
  a median of 3.63 ms before and 3.73 ms after; the 64 rounds a block cost what they cost, and reading a block from
  the input rather than from a copy saves a copy, not a round. The `sha256Hex` medians at a million units (6.98 ms
  before, 6.28 to 9.99 ms across four runs after) spread wider than any difference between them, because other
  workers were building on the machine. The timings were taken under the campaign's benchmark lock, which excludes
  other timed runs but not builds. The small-input rows, where the fixed cost of the padding copy and the hex
  `StringBuilder` showed, are faster: `sha256Hex` at 64 units has a median of 0.0007 ms where it had 0.0011.
- **The falsifier held both ways.** Every case checked its answer against the platform encoder and digest before it
  was timed. The suite's padding sweep and the new straddling-unit test were run against a deliberately wrong tail
  size (`rest < 57`), and five tests failed; restored, all nineteen `Hash` tests pass.
