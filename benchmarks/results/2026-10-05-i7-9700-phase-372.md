# Wire layer timing — 2026-10-05 — i7-9700 — Phase 372 (an integer past Int32 is parsed without an exception under node)

Phase 367's profile found `Json.readInt32` at 30 to 33 per cent of the node parse of the `floats`
corpus. Phase 372 measured that again, on `floats` and on the op-stream corpus. It then made the reader
refuse a token with more than ten significant digits before it calls the platform parser. This file
records the threshold, which was written down before any profile was taken, the profiles, and the
before and after figures. How to run and read the tables:
[`docs/wire-performance.md`](../../docs/wire-performance.md). The previous file on the same tokens:
[`2026-10-05-i7-9700-phase-367.md`](2026-10-05-i7-9700-phase-367.md).

- **Machine:** Intel Core i7-9700 @ 3.00 GHz, 8 logical processors, Windows 10.0.26200, mains power.
  Another worker's build and test load was running on the same machine during every measurement, so
  single cells can move by more than they did in earlier files. That is why each result below comes
  from several runs.
- **.NET:** SDK 10.0.401, Release build of `benchmarks/Fuaran.Core.Wire.Benchmarks`.
- **node:** v25.9.0. **Fable:** 5.0.0 (fable-library-js 5.0.0). The harness was compiled to a scratch
  directory by a checkout that owns a Fable toolchain (DECISIONS.md D55), once for each tree.
- **Trees:** before, fuaran-core at `1dcaa4d` (Phases 364 to 370); after, the same plus this phase's
  `src/` change. No corpus changed, and the pins in `Corpus.fs` did not move.
- **Agreement:** in every harness run, the 20 case fingerprints were identical on .NET and node and
  matched the pins before anything was timed.

## Why it cost what it did

Fable compiles `Int32.TryParse` to `tryParse` in `fable-library-js`'s `Int32.js`. That function wraps
`parse` in `try … catch`, and `parse` *throws* when the value is outside the range. So every integer
token that is too large for Int32 builds an `Exception`, with its message and stack, and then discards
it. .NET's `TryParse` returns `false` without throwing. A token reaches `readInt32` whenever it has no
`.` and no exponent. That includes the whole doubles past 2^53 that the float layout writes as 16- or
17-digit integers (one number in eight in `floats`), and every millisecond timestamp.

## The threshold, stated before the profile

`Json_readInt32` was called MATERIAL on a corpus if it was at least 5 per cent of the inclusive time of
`Json.parse` under node, in both profile runs. Phase 367 chose that figure as the smallest change these
tables resolve, and the same figure was used here. The change would be made if the reader was material on `floats`. The
falsifier was also written down: after the change, `readInt32`'s share of `floats` must fall below 5 per
cent, and the node `floats` parse must move by more than its run-to-run spread. If neither happens, the
attribution was wrong.

## A premise checked: the op-stream corpus has no millisecond timestamps

The shard asked for the op-stream corpus "with realistic timestamps". Phase 364's op-stream records
carry their time as an ISO string (`"at":"2026-10-04T…Z"`), and so do the roadmap engine's real
op-stream files. The only integer in a record is a small Lamport clock. So the op-stream corpus does not
contain the token shape this phase is about. It was measured as it is, to show the cost on a decode with
no large integers. It was also measured as **`op-stream-ms`**, a scratch variant made only for this
file and not committed: the same rendered corpus with each record's `"at"` string replaced by the same
instant as integer epoch milliseconds (13 digits). That variant is what "realistic timestamps" asks
about. It is built in the profiling script, which does not change the frozen corpus.

affect that cost, and the change was never intended to. It is reported in the last section.

## The change

`readInt32` already scans the token once to check that it is a sign followed by digits. If the digits
after the sign number more than ten, the reader now skips the leading zeros, which it has always
accepted (`007` is 7). If more than ten digits remain, it returns `None` without calling the platform
parser. Int32's extremes have ten digits in each direction, so such a value is at least 10^10 in
magnitude, and the platform parser would return `None` on both hosts. A token of ten significant digits
or fewer still goes to the platform parser, which alone decides the ten-digit edge. A short token pays
one comparison.

**Both hosts run this path.** The shard said to put the change under `FABLE_COMPILER` only if .NET
gained nothing. Measured directly on .NET, in one process, interleaved, with a reversed order and an
A/A control (A/A within 4 per cent in both runs), over 1,250 tokens of each shape and two runs:

| tokens | before | after | after / before |
|---|---:|---:|---:|
| 17-digit whole doubles | 0.032, 0.038 ms | 0.016, 0.019 ms | 0.51, 0.49 (reversed 0.48, 0.49) |
| 13-digit epoch ms | 0.027, 0.033 ms | 0.014, 0.016 ms | 0.49, 0.49 (reversed 0.47, 0.47) |
| small integers | 0.018, 0.020 ms | 0.022, 0.025 ms | 1.23, 1.26 (reversed 1.21, 1.21) |

So .NET gains on the tokens this change is about, about 13 ns each, and pays about 4 ns on a small
integer. An unused branch added to the reader cost 1.3 ns on its own, so part of the 4 ns comes from the
code's shape rather than from the check. At the size of a parse, both effects are below what the harness
tables resolve, as shown below. One path for both hosts was chosen over a branch that only Fable
compiles, because this repository's gate does not run Fable (D55). A Fable-only branch would be code the
suite never executes, and that is the point Phase 367's own durability note made about its Fable-only
change.

## The accepted and refused numbers did not move

- **node vs node vs .NET.** A pool of 161,622 tokens was built deterministically. It contains the Int32
  edges, with the ten-digit band on both sides of 2,147,483,647 and of 9,999,999,999. It contains 2^53,
  1e16, 1e17 and 2^63, each with no sign, a `-` and a `+`, and with 0, 1, 2, 5 and 12 leading zeros.
  It contains every run of zeros (so `-0`), 120,000 generated digit strings of 1 to 24 digits with
  signs and leading zeros, 20,000 epoch-millisecond values, and malformed shapes (white space, a second
  sign, a letter, an Arabic-Indic digit, a trailing NUL). Each token was given to `readInt32`, and
  parsed bare, in an array and as a member value: 646,488 outcome lines. Each line is the reader's
  answer, or the decoded value with its case (`JInt` and `JFloat` render alike, so the case is listed),
  or the refusal's kind, position and message. The Fable output before the change, the Fable output
  after it, and .NET after it gave **byte-identical** listings.
- **The comparison can fail.** The same listing with every refusal position moved by one differs on
  all 309,095 refusal lines. A copy of the after output with the edge moved to nine digits differs on 9,034 lines,
  for example reading `2147483347` as `JFloat` instead of `JInt`.
- **.NET, in the suite** (`ReadInt32DigitCountTests.fs`). The reader as it was before the phase is kept
  verbatim as the reference. Production is compared with it over 26,031 tokens built around the same
  edges, plus the integer tokens of the `floats` and op-stream corpora. Every JSON number among them is
  also compared through `parseDetailed`, bare, in an array and as a member value. Named pins cover both
  Int32 edges, a plus sign, `-0`, twelve leading zeros on each edge, the largest ten-digit token, the
  first eleven-digit token, a millisecond timestamp, and a whole double past 2^53 that still reaches the
  Phase-253 check. Two plausible wrong readers fail against the reference: one that counts raw digits,
  leading zeros included, and one whose edge is a digit short. Production itself was then deliberately
  broken to count raw digits. Two of the suite's six tests failed, 4,249 of 26,031 tokens disagreed,
  and the break was reverted.
- **The proof cone.** The JsonParse model's `int32_fits` already decides by the digits: it strips the
  leading zeros, then compares length and digits with the Int32 limits. So the model describes this
  reader no less exactly than it described the old one. Neither the model nor the oracle moved. The leg
  was re-run green: `proofs/check.ps1 -Modules JsonParse` verified JsonParse.fst, found the oracle
  byte-identical to a fresh extraction, and Proofs.Oracle passed 160 tests.

## What the figures say

- **The exception was the cost.** Removing it makes the node `floats` parse 34 to 38 per cent faster
  and the `op-stream-ms` parse 8 to 14 per cent faster. `readInt32` falls from about a third of a
  `floats` parse to under 3 per cent. On .NET the change is level at the size of a parse, about twice
  as fast per long token, and about 4 ns slower per small integer.
- **Phase 364's op-stream corpus carries no integer timestamps**, and neither does the engine's own op
  stream. So the "timestamp" benefit applies to a consumer whose documents carry epoch-millisecond
  integers. It does not apply to the op-stream format as it stands.
- **The next cost on integers is the ordinary parse.** Under node, Fable's in-range `Int32.parse` (a
  regular-expression check, then `Number.parseInt`) is 6 to 8 per cent of a parse of the op-stream
  corpus, whose only integers are 500 small Lamport clocks. Reading the value from the digits that
  `readInt32` has already scanned, for up to nine significant digits, would avoid it. That needs no
  call to the platform parser at all. This phase does not do it: the shard keeps the platform call for
  every token that can fit. It is reported for its own phase.
