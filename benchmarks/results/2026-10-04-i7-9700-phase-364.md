# Wire layer timing — 2026-10-04 — i7-9700 — Phase 364 (the "before" baseline)

The first two-host measurement of `Fuaran.Core.Wire`, taken before any wire speed-up. Phases 365 and
later cite these tables as their "before". How to run and read them: [`docs/wire-performance.md`](../../docs/wire-performance.md).

- **Machine:** Intel Core i7-9700 @ 3.00 GHz, 8 logical processors, Windows 10.0.26200, mains power.
- **.NET:** SDK 10.0.401, Release build of `benchmarks/Fuaran.Core.Wire.Benchmarks`.
- **node:** v25.9.0. **Fable:** 5.0.0 (fable-library-js 5.0.0). The tool came from the Fable toolchain
  of a checkout that owns one, and it compiled the harness to a scratch directory (DECISIONS.md D55).
- **Tree:** fuaran-core `phase-364` (based on `a9ca552`), with no change to `src/`.
- **Command:** `pwsh ./benchmarks/run.ps1 -Runs 15 -NodeEntry <fable output>/Program.js`, run twice back
  to back on an otherwise idle machine.
- **Agreement:** all 16 case fingerprints were identical on .NET and node, and each host matched the
  pins in `Corpus.fs`, before anything was timed.

Figures are the median of 15 samples, in milliseconds per call. Each sample is batched to at least
50 ms of wall clock. The corpora: (a) `escape-free` and (b) `escape-heavy` are 1,000 strings of 64
characters each, (c) `op-stream` is 500 op-stream-shaped records, and (d) `state` is the compute
incremental state's shape with 20,000 tokens. The `escape` column escapes every string and key the
value carries. `parse` parses the `render` text.

## What the baseline says

- **Run-to-run spread is real, so compare like with like.** Most cells moved by under 15 per cent
  between the two runs. Three cells moved by much more: node `escape-free` render (3.4 to 7.5 ms),
  node `escape-free` escape (3.0 to 4.4 ms) and .NET `state` parse (9.8 to 12.8 ms). An "after"
  figure should come from two runs of the same command on the same machine, and a change smaller
  than the spread of its cell is not evidence.
- **Escaping is the node bottleneck.** node takes 8 to 12 times as long as .NET to escape, and render
  and canon follow it, since both escape every string. Escape-heavy text costs node about 4 times what
  escape-free text costs, per character. That is the cost an escape fast path (Phase 365) has to move.
- **node parses relatively well.** node is 3 to 5 times slower than .NET at parsing, and level with it
  on `state`.
- **Most of .NET's `state` parse is the collector, not the parser.** The suite's clock leg times the
  same parse with the collector held off. It reads 1.8 to 2.0 ms at 20,000 tokens and 14.6 to 16.8 ms
  at 160,000, which is linear. The table's 9.8 to 12.8 ms is that work plus the gen0/gen1 promotion of
  the growing result. Under workstation GC (measured with `DOTNET_gcServer=0`), the per-token cost
  more than doubles between 5,000 and 10,000 tokens (128 ns to 283 ns per token) and reaches about
  400 ns per token at 80,000. Under server GC it
  stays flat at 93 to 109 ns per token from 1,250 to 160,000 tokens. One parse of the 20,000-token
  state allocates 5.5 MB and one render 6.6 MB. So a parse speed-up (Phase 366) that does not also
  allocate less will move the node column more than the .NET `state` cell.
