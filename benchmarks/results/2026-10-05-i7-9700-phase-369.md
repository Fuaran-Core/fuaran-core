# Op-stream load timing — 2026-10-05 — i7-9700 — Phase 369 (the JSONL line decoder reads by runs)

Phase 369 changed how an op-stream line's string tokens are decoded. `Jsonl.decodeString` (in
`Fuaran.Core.OpStream`) decodes a token that `skipString` has already scanned and accepted. Its caller
first copied the token out of the line, and it then appended the body to a builder one character at a
time. It now reads the token in place: a body with no backslash is returned whole, by one `Substring`;
otherwise each escape-free run is copied by one ranged `Append`, and only the escapes are decoded one by
one. `skipString` is unchanged, so every refusal and its position are unchanged. The wire harness's
earlier baselines are [`364`](2026-10-04-i7-9700-phase-364.md) to [`368`](2026-10-05-i7-9700-phase-368.md);
how to compile for node is in [`docs/wire-performance.md`](../../docs/wire-performance.md).

- **Machine:** Intel Core i7-9700 @ 3.00 GHz, 8 logical processors, Windows 10.0.26200, mains power.
  Another worker's builds and test runs were using the machine at the same time, which is why every
  figure below is from alternated runs and is read against its spread.
- **.NET:** SDK 10.0.401, Release builds.
- **node:** v25.9.0. **Fable:** 5.0.0 (fable-library-js 5.0.0), from the toolchain of a checkout that
  owns one, compiling to a scratch directory (DECISIONS.md D55). Each tree was compiled separately.
- **Trees:** before, fuaran-core `main` at `a5381ee` (365 to 368 landed); after, the same plus this
  phase's `src/` change.

## How it was measured, and why not by `benchmarks/run.ps1`

The wire harness (Phase 364) times `Fuaran.Core.Wire` only; it references neither `Fuaran.Core.OpStream`
nor a stream witness, so it has no op-stream load or verify case. Adding one would widen the harness's
project, corpus pins and fingerprints for a measurement this phase makes once. The figures were taken
instead by scratch programs, not committed, as Phase 368 did. They use the harness's own timing rule:
`Harness.medianMs`, copied (two warm-up calls, calls per sample doubled until one sample spans 50 ms,
then the median sample, in ms per call, read from the wall clock so that node and .NET measure the same
thing).

- **Corpora.** Two streams of 2,000 records each, built with `OpStream.appendMany` and the default
  (FNV-1a) hash, then written with `OpStream.toJsonl`. Every op is a 160-byte object, so the line shape
  is a store's. `plain` uses an agent actor (`kind`, `model`, `version`, `id`; no escape anywhere in the
  decoded tokens). `escaped-actor` uses a human actor whose id carries a quote, a backslash, a tab, a
  `/`, an é and a U+0001, so one decoded value per line holds escapes. Each line decodes 15 string
  tokens (`plain`) or 11 (`escaped-actor`): the member keys, the actor's members, `prevHash` and `hash`.
  The op itself is handed to the witness as a raw span and is not decoded here.
- **Cases.** `load` is `OpStream.fromJsonl`; `verify` is `OpStream.fromJsonlVerified` with the default
  hash. Each run first checks that the stream verifies and holds 2,000 records.
- **Whole-load figures** are separate processes for the two trees, alternated before/after. Five pairs
  were run on both hosts, then five more on .NET, each at 21 samples.
- **The decoder alone** was timed in one process. It used verbatim copies of the old and the new
  `decodeString`, over exactly the tokens a load decodes from each corpus. The old decoder was paired with
  its call site's `Substring`, the new one read in place. Cases were interleaved, the order rotated every
  round, 31 rounds. An A/A control timed the old decoder a second time. Before timing, the two copies were
  checked to agree on every token.
- **Bytes allocated per call** on .NET are from `GC.GetAllocatedBytesForCurrentThread` over 50 calls,
  after five warm-up calls.

The A/A control is within 1 to 4 per cent of the first reading in every run. Under node, the old decoder

the node load moves below. On .NET it was about a tenth.

## The values and refusals did not move

- **.NET, in the suite** (`JsonlDecodeRunTests.fs`). `decodeString` is private, so it is reached through
  every public route that calls it: `unquote` (a whole token), `parseLine` / `topFields` (a member key),
  `stringField` (a member value) and `stringsField` (array items). Each is compared with the decoder as
  it stood before the phase, kept as a reference. The sweep covers every sequence of up to four tokens
  from a 22-token run-boundary alphabet: runs, each raw surrogate half, every short escape, `\u` escapes
  of a BMP character and of a pair, every malformed escape, a trailing backslash and a bare quote. That is
  245,411 inputs, and a token `unquote` refuses must be refused by the line too. Thirteen named faults
  state their `JsonlFaultReason` and `Position`: an unknown escape at the start, middle and end of a run,
  straight after an escape and after an escape and a run; a short `\u`; each lone surrogate half; a high
  half followed by a non-low escape; an unterminated string inside a run, on a trailing backslash and
  after an escape; and a fault inside a key. Two broken run decoders are red against the reference (one
  copies the first run one unit short, one drops the run after an escape). Production itself was broken
  once the same way (the first run copied one unit short): the sweep and the escape test went red, and
  the change was reverted.
- **Both hosts.** The before and after trees were each compiled for .NET and by Fable and run over the
  same 137,561-input sweep: 19 alphabet tokens, up to four deep, each as a whole token, a key, a value and
  two array items. 98,558 of the inputs are refusals. The four outcome listings, value or refusal reason
  and position, were byte-identical (MD5 `e0ea10d4…` for each).
- **Unchanged suites.** The Phase 296 scanner laws (`OpStream.Jsonl`), the `OpStream` and `Dag` suites
  (`Dag`'s node reader goes through the same routes) and every committed vector are green with no
  re-hash. The decoder changes no byte that is written.

## What the figures say

- **Under node, a store load is 21 to 30 per cent faster** and a verified load 12 to 20 per cent faster.
  Per string token, the decoder is 3 to 6 times faster: an escape-free token is now one `Substring` of the
  line, where it was a `Substring` and then a character-by-character builder.
- **On .NET, a load allocates 22 to 26 per cent less.** The decoder alone is 1.9 to 2.6 times faster. In
  the whole load that shows clearly only on `escaped-actor` (12 to 14 per cent); on `plain` it is inside
  the collector's spread.
- **Verify gains less than load** because the chain hash is unchanged and is a larger share of it.
