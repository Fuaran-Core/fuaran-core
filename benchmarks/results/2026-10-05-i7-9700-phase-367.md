# Wire layer timing — 2026-10-05 — i7-9700 — Phase 367 (the parsed-float check, measured under node)

Phase 367 asked whether the parser's float round-trip check costs a material share of a decode under
node, and said to replace it with a digit comparison only if it does. This file records the profile,
the threshold the verdict was judged against (written down before any profile was taken), and the
before and after figures. How to run and read the tables:
[`docs/wire-performance.md`](../../docs/wire-performance.md). Earlier baselines:
[`2026-10-04-i7-9700-phase-364.md`](2026-10-04-i7-9700-phase-364.md),
[`2026-10-05-i7-9700-phase-365.md`](2026-10-05-i7-9700-phase-365.md),
[`2026-10-05-i7-9700-phase-366.md`](2026-10-05-i7-9700-phase-366.md).

- **Machine:** Intel Core i7-9700 @ 3.00 GHz, 8 logical processors, Windows 10.0.26200, mains power.
- **.NET:** SDK 10.0.401, Release build of `benchmarks/Fuaran.Core.Wire.Benchmarks`.
- **node:** v25.9.0. **Fable:** 5.0.0 (fable-library-js 5.0.0), from the toolchain of a checkout that
  owns one, compiling the harness to a scratch directory (DECISIONS.md D55). Each tree was compiled
  separately.
- **Trees:** before, fuaran-core `phase-367` at `d56f3da` plus this phase's new corpus (no change to
  `src/`); after, the same with this phase's `src/` change.
- **Command:** `pwsh ./benchmarks/run.ps1 -Runs 15 -NodeEntry <fable output>/Program.js`, twice for
  each tree; then the node parsers before and after in one process, interleaved, twice (below).
- **Agreement:** in all four runs, the 20 case fingerprints were identical on .NET and node and matched
  the pins in `Corpus.fs` before anything was timed.

## The new corpus: `floats`

Phase 364's four corpora carry one float per op-stream record and none elsewhere, so no table timed a
decode made mostly of numbers. `floats` is 10,000 floats in one array, eight layouts in turn: short and
long fractions, a negative, a small number and a large one in the `E` layout, a short half, a
thousandth — and, one in eight, a WHOLE double past 2^53 (between 9.1e15 and 1e16 + 131,042), which the
float layout writes as a 16- or 17-digit integer token. It is pinned like the others; the four earlier
corpora's pins did not move. A suite test now also requires one pin per corpus and case, because
`unpinned` compares only the pins a corpus has and a new corpus with none passed it.

## What the shard assumed, and what the code does

The shard says the parser "accepts a float token only if `FloatLayout.finite` of the parsed value
reproduces the token, so every float in a decode is rendered again". **It does not.** A token with a
`.` or an exponent is read by `Double.TryParse` and the finiteness gate alone. The re-render runs on one
token shape only: an integer token past the int53 range (17 or more digits, or 16 digits above
9007199254740992), which Phase 253 admits exactly when it is the canonical layout of the double it reads
as. The Fable output agrees: `FloatLayout_finite` has one call site in the parser, on that path. In
`floats` that is the one-in-eight slice, 1,250 tokens per parse. On a decode of fractional floats the
check costs nothing.

## The threshold, stated before the profile

MATERIAL meant both of these:

- (a) the check is at least 5 per cent of the inclusive time of `Json.parse` on `floats` under node, in
  both profile runs;
- (b) removing it would move the harness's parse cell by more than that cell's own run-to-run spread.

5 per cent was chosen for three reasons. It is about the smallest change these tables can resolve: Phase
366's parse cells moved 4 to 25 per cent between back-to-back runs of the same code. The replacement adds
a second acceptance procedure inside the JsonParse proof cone, which must then stay identical on two
hosts. And the check itself is the upper bound on what any rewrite of it can save.

## The profile (before)

`node --cpu-prof --cpu-prof-interval 100` over 400 parses of `floats`, attributed only to samples
inside `Json_parseDetailedWithPolicy`, inclusive. Two runs:

| function (inclusive, share of parse) | run 1 | run 2 |
|---|---:|---:|
| `Json_readInt32` (Fable `Int32.tryParse`) | 30.4% | 30.3% |
| `Double.tryParse` | 16.3% | 16.7% |
| **`FloatLayout_finite` (the check), of which `reLay`** | **14.0%**, 13.7% | **12.6%**, 12.2% |
| `Json_isJsonNumber` | 13.0% | 12.8% |

As a second check, `FloatLayout.finite v = tok` was timed directly over exactly the 1,250 (value,
token) pairs a parse asks it about. Under node that took 0.889 and 0.881 ms per parse, against a parse of
9.63 and 9.12 ms in the same process: 9.2 and 9.7 per cent. On .NET it took 0.266 and 0.157 ms against
2.90 and 2.83 ms: 9.2 and 5.5 per cent. Removing it entirely would save about 0.9 ms of node's 7.3 to
7.6 ms `floats` parse cell, whose spread between the two runs below was 0.37 ms. **Both conditions
hold, so the check is material on this corpus.** It is material only in proportion to how many tokens
are whole doubles past 2^53.

## The change

`FloatLayout.isFiniteLayout v tok` (internal) answers `finite v = tok`, exactly, for every `v` and `tok`.
Under Fable, every double with magnitude in [2^53, 1e17) is whole. For such a double, JS's `toString`
writes the integer digits with no exponent and no point. `reLay` starts from that same string, finds
the base-10 exponent at 15 or 16, inside its fixed-point range, and writes the same characters back. In
that band the comparison is therefore `v.toString() === tok`, with no re-lay. Outside the band, and on
.NET, where "R" is already the shortest digits, it is `finite v = tok` unchanged. `parseNumber` asks
this instead of `finite v = tok`. Timed over the same 1,250 pairs under node, the comparison went from
0.925 ms to 0.075 ms per parse.

## The accepted and refused numbers did not move

- **node vs node vs .NET.** A pool of 590,283 number tokens was built deterministically. It holds the
  oracle suite's named number inputs, 2^53 ± 3,000, 1e15, 1e16 and 1e17 ± up to 3,000, 2^54, the
  largest double below 1e17, 1e18, 1e19, 2^63 and 1e21, all with both signs. It also holds the layouts
  of 60,000 generated whole doubles from 2^50 to 2^57, each with seven near misses (±1, +2, a trailing
  zero, the last digit dropped or changed), plus 60,000 random digit strings of 1 to 22 digits and the
  point and exponent spellings. Each token was parsed bare, in an array and as a member value: 1,770,849
  inputs, 1,286,982 accepted and 483,867 refused. 240,976 tokens reach the check, 181,804 of them in the
  `toString` band, and 87,099 are admitted. The Fable output before the change, the Fable output after
  it, and .NET after it gave **byte-identical** outcome listings: the value, or the refusal's kind,
  message and position.
- **The comparison can fail.** The same listing with every refusal position moved by one differs on all
  483,867 refusals. A Fable build with the band widened to 1e21 differs on 60,231 inputs, for example
  admitting `100000000000000000` as `1E+17`.
- **.NET, in the suite** (`FloatLayoutCheckTests.fs`). The reader's decision as it stood before the phase
  is kept verbatim as the reference. Production is compared with it over 39,432 tokens (bare and in an
  array), with the boundary stated by name on both sides of 2^53 and of 1e17. Two plausible wrong
  checks fail against the reference: no check at all, and a comparison against the double's exact
  digits rather than its shortest. Production itself, broken to compare exact digits, failed three of
  the suite's five tests and was then reverted.
- **The proof cone.** The JsonParse model takes the float reader as a parameter (`freadv`, with
  `FCanonical` meaning that the canonical layout IS the token). This phase changes how that verdict is
  computed, not what it is, so neither the model nor the oracle moved. The JsonParse leg was re-run
  green.

## What the figures say

- **The shard's premise was wrong about which floats pay.** Fractional floats never paid for the
  round-trip check. Only integer tokens past 2^53 did, and on those it cost about 0.7 µs each under node
  and about 0.15 µs on .NET.
- **Where those tokens are one in eight, it was material**, 9 to 14 per cent of a node parse. The change
  makes the node `floats` parse 16 to 20 per cent faster in one process, against a ±6 per cent A/A
  control. On every other corpus, and on .NET, it changes nothing measurable.
- **The next cost on the same tokens is bigger.** `Json.readInt32` is 30 to 33 per cent of the node
  `floats` parse. Fable's `Int32.tryParse` throws, and catches, an exception for every integer token
  outside the Int32 range. So under node every integer token past 2^31 pays for an exception before it
  reaches the int53 guard, and that includes the common case of a millisecond timestamp. This phase does
  not touch it. It is reported for its own phase.
- **Node renders `floats` six times slower than .NET** (render 5.9 to 6.4 times, canon 6.2 to 7.7
  times), because every float is re-laid on the way out. That is outside this phase too.
