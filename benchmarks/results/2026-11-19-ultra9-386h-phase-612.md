# Aggregating a date, a timestamp or a bool column — 2026-11-19 — Core Ultra 9 386H — Phase 612

Phase 612 asked whether `Column.aggregate`, which compared a bool, date or timestamp column's rows as the cells they
render (`Min` and `Max` through `Cell.compare`, `CountDistinct` through `Cell.token`), cost the per-group and per-row
paths that call it a material share of their time or allocation, and, if it did, to compare and key the stored values
themselves. The shard estimated the cost from reading the code; this file is the measurement, taken before any
change, and the same measurement after it.

## Was it material?

The threshold was written down before the baseline run: MATERIAL means that on the named path, `Column.aggregate
Max` over a 100,000-row millisecond timestamp column, the bytes a comparison of the stored values would not allocate
are at least 5 % of what one call allocates, or its median time is at least 20 % above a loop over the stored values
would need, or the call collects generation 2. A loop over the stored values allocates nothing per row, so the
first test is met when at least 5 % of the call's bytes are allocated per row.

The named path allocated 598.4 bytes a row before the change, all of it per row: the cell each row renders and
the parses and substrings of each comparison. The cost was material, so the change went ahead.

## The run

- **Machine:** Intel Core Ultra 9 386H, 16 logical processors, Windows 10.0.26300, mains power.
- **.NET:** SDK 10.0.203 (runtime 10.0.8), Release build of the column package the harness references.
- **Harness:** [`temporal-aggregate-phase-612.fsx`](temporal-aggregate-phase-612.fsx), beside this file, run as its
  header says (`dotnet fsi --optimize+ benchmarks/results/temporal-aggregate-phase-612.fsx`). Each case runs in its
  own process. The input is built outside the timed closure. Each case warms up for three seconds of wall-clock
  time, then samples until a ten-second budget is spent (at least five samples, at most 2,000). Every case checks
  its answer before it is timed, against one computed from the stored values with no cell.
- **Load:** both runs were taken holding a shared benchmark lock, so no other measured run was alongside them; builds
  by other sessions may still have been running. The allocated bytes and gen2 counts do not depend on load and are
  the primary evidence.
- **Columns:** wall time per call in milliseconds (mean, median, p95), the bytes the calling thread allocated per
  call and per row, and generation-2 collections per call. One call aggregates all 100,000 rows once.

## The cases

- **`Max` and `Min` over a millisecond timestamp column** of 100,000 instants spread over `0001`..`9999`, one in
  ten with a zero fraction. `Max` is the acceptance's named path.
- **`CountDistinct` over the same column.**
- **`Max` and `CountDistinct` over a date column** of 100,000 days over the same range.
- **`Max` and `CountDistinct` over a bool column**, one row in seven `true`.

## Reading it

- **The named path: `Max` over the millisecond timestamp column allocates 208 bytes a call where it allocated
  59.8 MB**, and its median falls from 13.37 ms to 0.27 ms. What is left is the answer: one cell, its text, the
  `Ok` and the comparison's closure. Before, every row rendered its cell, and every comparison parsed both texts
  and took up to four substrings.
- **`Max` over the date column** allocates 160 bytes where it allocated 15.2 MB (3.65 ms to 0.13 ms), and **over
  the bool column** 56 where it allocated 4.8 MB (0.75 ms to 0.05 ms): before, each row built a cell and each
  comparison an option.
- **`CountDistinct`** keys the stored values in a hash set, so it still allocates the set: 84.5 bytes a row over the
  timestamp column where it allocated 314.0 (median 9.85 ms to 3.52 ms), and 48.3 where 236.4 over the date column
  (7.70 ms to 1.31 ms), every row distinct in both. Over a bool column it is two flags, 56 bytes where 5.6 MB.
- **The range scan.** A date or timestamp column takes the typed arm only when every present value is in the
  canonical range, which costs one more read of the column before the aggregate; it is inside the figures above.
  A column holding a day or an instant outside the range, which `aggregate` must still answer because it does not
  validate, is read as the cells it renders, exactly as before, so its cost is the "before" row.
- **No answer moved:** the Phase 421 differential, which holds `aggregate` to the cell walk it replaced over 26,000
  drawn columns with days, seconds and fractions outside the range among them, passes unchanged; new tests hold the
  out-of-range cases by name (`10000-01-01` against `2026-01-01`, a half second, a fraction of the unit's scale)
  and the named path's allocation. With the range guard removed, both the differential and the new cases fail; on
  the tree before the change, the allocation test fails.
