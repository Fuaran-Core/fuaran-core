# Migration: pluggable op-stream payload format (`0.0.1-alpha.5`, Phase 255 / finding F4)

**What changed.** `Fuaran.Core.OpStream` gained a `StreamConfig` — the chain *payload* binding —
alongside the existing pluggable `HashFn`. The chain hash is `hashFn prevHash (payload seq actor
opJson)`; before alpha.5 the `payload` and the genesis sentinel were hard-coded to the canonical
`{seq,actor,op}` envelope + `""`. Now they are pluggable, so a domain can match its **own legacy
chain format** during migration, verify its persisted streams, then cut over to canonical with no
flag-day re-hash.

**Why.** Re-expressing a domain's op-stream over Core changes the chain hashes — a stream persisted
under a domain's own format (Documents `"%d|%s|%s|%s"` + `"genesis"`, Calc `fuaran-calc/op-stream@1`,
Geom's hand-rolled JSON — three distinct formats observed across the adoption pilots) will not
`verifyChain` under Core's canonical binding. Without a config seam the only migration is "re-hash
every persisted stream at once" — a flag day no regulated-document deployment accepts.

## Surface

```fsharp
type StreamConfig =
    { Payload: int -> string -> string -> string   // seq -> actor -> opJson -> payload
      Genesis: string }                            // the first record's PrevHash sentinel

// inside module OpStream:
val canonicalConfig : StreamConfig                 // {seq,actor,op} + "" — the pre-255 default
val appendWith      : StreamConfig -> HashFn -> StreamWitness<_,_,_> -> string -> 'Op -> 'State -> OpRecord<'Op> list -> Result<'State * OpRecord<'Op> list, 'Rej>
val verifyChainWith : StreamConfig -> HashFn -> StreamWitness<_,_,_> -> OpRecord<'Op> list -> bool
val rehash          : StreamConfig -> StreamConfig -> HashFn -> StreamWitness<_,_,_> -> OpRecord<'Op> list -> Result<OpRecord<'Op> list, string>
```

`append` / `verifyChain` are unchanged — they delegate to `appendWith` / `verifyChainWith` with
`canonicalConfig`, which is **byte-identical** to the pre-alpha.5 behaviour (regression-locked). No
existing call site changes.

## Migration recipe (a domain with persisted legacy streams)

1. **Describe the legacy format** as a `StreamConfig` — the domain's pre-Core payload string + its
   genesis sentinel. Example (a Documents-style chain):

   ```fsharp
   let legacy : StreamConfig =
       { Payload = fun seq actor opJson -> sprintf "%d|%s|%s" seq actor opJson
         Genesis = "genesis" }
   ```

2. **Verify the persisted stream** under that config — proves the records you are about to migrate
   are intact before you touch them:

   ```fsharp
   if not (OpStream.verifyChainWith legacy OpStream.defaultHash sw records) then
       // refuse — the source chain is corrupt or the config does not match
   ```

3. **Rehash to canonical.** `rehash` re-verifies under `fromCfg` (returning a named `Error` if the
   source does not verify — it never silently re-blesses a broken chain) then re-derives every
   `PrevHash` / `Hash` under `toCfg`. The ops / actors / seqs are the source of truth; only the hash
   chain changes:

   ```fsharp
   match OpStream.rehash legacy OpStream.canonicalConfig OpStream.defaultHash sw records with
   | Ok canonical -> // canonical |> verifyChain defaultHash sw  ==>  true; persist it
   | Error e       -> // legacy chain did not verify under `legacy` — investigate, do not migrate
   ```

4. **Cut over.** After migration, drop the legacy config and use the plain `append` / `verifyChain`.
   A domain that never persisted streams in another format skips all of this — `canonicalConfig` is
   the default.

## Verification

`Fuaran.Core.Tests.OpStreamTests` (Phase 255 block): `appendWith canonicalConfig` reproduces the
default chain exactly; a legacy-format chain verifies under its own config and **not** under the
default; `rehash` migrates it to a canonical chain that `verifyChain`s under the default with ops
preserved and replay-state unchanged; `rehash` refuses a tampered source chain.

## Rollback

Purely additive — to roll back, ignore the new surface. `append` / `verifyChain` / `replay` are
unchanged, so a consumer pinned to alpha.4 behaviour needs no code change on alpha.5.
